## 1. Executive Summary

Ground-truth demand targets in the SmartCanteen AI architecture are derived from register-level transactions recorded during meal services. In Phase 7 and 8, an ingestion engine (`POST /api/pilot/pos/import`) was built and hardened to validate schema conformity, prevent duplicate transactions within batches, ensure idempotent re-imports, and reject records for unscheduled services.

However, **the software ingestion engine cannot be considered verified for production until an authentic export generated by the physical canteen register is tested against the pipeline.** This document specifies the register export interface, field mappings, financial reconciliation logic, and the remaining physical verification requirements.

## 4. Operational Transaction Nuances & Demand Reconciliation

A primary risk in demand forecasting is assuming that **gross register sales** equal **actual food portions consumed**. Operational canteen cashiering involves several distinct transaction types that must be reconciled:

```
+----------------------------------------------------------------------------------------------------+
|                                  Register Transaction Flow                                         |
+-----------------------------------+-----------------------------------+----------------------------+
| Normal Paid Sales                 | Complimentary / Staff Meals       | Voids & Cancellations      |
| (1 Swipe = 1 Portion Dispensed)   | (0 Price = 1 Portion Dispensed)   | (Pre vs Post-Dispense)     |
+-----------------------------------+-----------------------------------+----------------------------+
```

### 4.1 Reconciliation Categories

1. **Normal Paid Sales**:
   - Customer pays via student ID badge, credit card, or cash.
   - **Reconciliation Rule**: Portions dispensed = Transaction quantity.
2. **Complimentary / Staff Duty Meals**:
   - Cooks, stewards, and campus security receive duty meals logged with a $100\%$ discount code or voucher ($0.00 gross revenue).
   - **Reconciliation Rule**: **Food is dispensed and consumed.** Must be included in `portions_served` for demand forecasting, regardless of zero financial sales.
3. **Pre-Dispense Voids (Order Mistake at Register)**:
   - Cashier accidentally rings a dish, customer changes mind before plate is served; cashier voids transaction.
   - **Reconciliation Rule**: Food was never plated. Must NOT count as a portion dispensed.
4. **Post-Dispense Returns (Dropped Tray / Contamination)**:
   - Customer drops plate immediately after leaving register; supervisor approves free replacement.
   - **Reconciliation Rule**: Kitchen prepared and dispensed two physical portions, but register reflects one net sale. Physical waste weighing (plate waste) must capture the dropped portion.

### 4.2 Mathematical Ground-Truth Demand Formula
$$\text{Expected\_Demand\_Portions} = \sum \text{Paid\_Portions} + \sum \text{Complimentary\_Portions} + \text{Unserved\_Surplus\_Portions}$$
$$\text{Where } \text{Cooked\_Portions} \approx \text{Portions\_Served} + \text{Unserved\_Surplus\_Portions} + \text{Production\_Loss}$$

## 5. Automated Validation Enforced in Ingestion Engine

The backend ingestion handler (`import_pos_csv` in `backend/app/pilot/service.py`) executes the following automated checks:

1. **Batch-Internal Deduplication**: Tracks seen tuples `(date, period, section, dish)` within the incoming file. Identical rows in the same file are dropped with a warning.
2. **Database Idempotency**: If the entire file or row was already ingested in a previous upload, existing records are retained and duplicate insertions skipped.
3. **Unscheduled Service Protection**: If a transaction references a date or meal period not registered in `meal_services`, the transaction is rejected with an explicit error.
4. **Payload Bounding**: Requests $> 2\text{ MB}$ return `HTTP 413 (Content Too Large)`.
5. **Partial Batch Resilience**: Valid rows are processed while invalid rows return actionable line-by-line feedback (`rejected_rows` with line numbers and reasons).
